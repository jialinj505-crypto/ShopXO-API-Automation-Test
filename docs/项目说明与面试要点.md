# ShopXO 电商平台 API 自动化测试 —— 项目说明与面试要点

> 用途：快速理解项目全貌 + 应对面试追问。
> 所有数字与结论都来自**真实执行结果**，可复现；被问到细节时照实说，不要编。

---

## 一、一分钟版本（建议背下来）

> 这是一个电商平台（ShopXO）的**接口自动化测试项目**，我负责框架设计和用例编写。
> 技术上用 **Pytest + Requests**，做了**五层分层架构**：用例层只写业务与断言，接口层封装路由，
> 核心层实现请求驱动、统一鉴权、断言、数据加载，配置层收敛环境差异，数据层放 JSON 测试数据。
> 框架重点解决四件事：**请求重试（带幂等保护）**、**统一 Token 鉴权封装**、
> **DDT 数据驱动（正向/边界/异常全覆盖）**、**环境自适应（能力不足自动跳过并说明原因，绝不假绿）**。
> 一共 **284 条用例**（98 条真实环境接口回归 + 186 条框架离线自测）覆盖登录、商品、搜索、购物车、订单、地址、用户中心等模块，
> 其中包含一条 **登录→搜索→加购→下单→取消的 E2E 闭环**；
> 最近一次全量回归 **265 通过 / 12 跳过 / 7 已知缺陷守护 / 0 失败，约 30 秒**（其中 186 条离线自测 1.3 秒跑完），
> 并且通过 **Allure 报告 + Jenkins 流水线**接入了持续回归。
> 另外，靠这套用例我实际发现了 **7 个可复现的接口缺陷**，比如加购不校验库存上限、订单列表状态筛选失效、
> 待付款订单评价接口"静默成功"等。

## 二、三分钟版本（面试官说"详细讲讲"）

**背景与目标**：被测系统是 ShopXO 开源电商（前台是 App 接口 `index.php?s=/api/*`，商家端是 `admin.php?s=/admin/*`）。
项目目标不是"写几条能跑的脚本"，而是要能**进 CI 持续回归**——所以必须解决稳定性（重试/数据清理/环境差异）
和可维护性（分层/数据驱动）问题。

**架构**：五层。
- `tests/` 用例层：只写业务场景和断言，通过 fixture 拿接口对象，通过 JSON 数据驱动参数化；
- `api_objects/` 接口层：一个类=一个业务模块（用户/商品/搜索/购物车/订单/地址/优惠券/商家），
  一个方法=一个接口，只声明路由、参数、鉴权方式、幂等性；
- `core/` 框架层：`base_api.py`（请求驱动：重试/超时/日志/附件/容错）、`auth.py`（统一 Token 封装）、
  `assert_helper.py`（统一断言）、`data_loader.py`（数据驱动）、`env_check.py`（环境能力探测）、
  `allure_utils.py`（报告适配，未装 Allure 自动降级）；
- `config/setting.py` 配置层：环境地址、超时重试策略、账号、目录，全部支持环境变量覆盖；
- `data/` 数据层：8 个 JSON 数据集 + 6 个响应 JSON Schema。

**关键设计（也是面试最容易被追问的）**：
1. **请求重试不是无脑重试**：网络异常/5xx/约定业务码才重试，退避策略 0.5s×2ⁿ、默认 2 次；
   下单、支付、评价这类**写操作通过 `idempotent=False` 强制禁用重试**，从机制上杜绝重复下单。
2. **统一 Token 鉴权**：token 由框架按接口文档自动注入（文档规定走 GET 参数），会话级缓存只登录一次，
   业务码 `-400`（登录失效）自动失效重登，`RLock` 保证并发安全，日志里 token 脱敏。
   用例里**看不到任何 token 拼接代码**。
3. **数据驱动**：用例数据全在 `data/*.json`，用 `group` 分场景、`expected_code` 断期望、
   `known_defect` 标记已知缺陷（自动转 xfail），新增用例只改数据不改代码。
4. **环境自适应**：会话开始探测环境能力（登录、关键路由、插件、后台入口），
   `@pytest.mark.requires("coupon")` 的用例在能力缺失时**自动跳过并写明原因**，
   结果同时写进 Allure 环境信息和 `reports/env_probe.json`。宁可明确跳过，也不做"假绿"。
5. **可观测性**：每条请求都有结构化日志；Allure 报告里带**可复现的 curl 命令 + 完整响应体**；
   失败按"产品缺陷/环境问题/用例问题"自动分类。

**结果**：284 条用例（98 条真实环境接口回归 + 186 条框架离线自测），5 层架构、44 个 Python 文件、
11 个接口测试模块 + 5 个框架离线单测文件；
265 passed / 12 skipped / 7 xfailed / 0 failed，全量约 30 秒（离线自测 1.3 秒）；
12 条跳过是因为公开沙箱没装优惠券插件、关了商家后台入口（代码与数据集已就绪，换环境即可执行）；
7 条 xfail 是我登记的 7 个真实缺陷。


## 五、九大技术亮点（每个都能展开讲 1~2 分钟）

### 1. 分层解耦：接口变了只改一个文件
用例层不出现 `requests`、不拼 URL；接口层不写断言；配置不写死在代码里。
好处：接口路径变化只改 `api_objects/*`；测试数据变化只改 `data/*.json`；换环境只改环境变量。
**举例**：接口文档里的 `api/search/datalist` 在实际环境是 404，我只改了 `SearchAPI` 一处
（换成实测可用的 `api/search/index`），10 条搜索用例零改动。

### 2. 请求重试 + 幂等保护（重点）
- 触发：网络异常（ConnectionError/Timeout）、HTTP 5xx、约定业务码（默认 -500）
- 退避：`interval × backoff^(n-1)`，默认 0.5s → 1s
- **幂等控制**：`idempotent=False` 的接口（`buy/add`、`order/pay`、`order/comments`、`cart/save`、
  `cart/delete`、`useraddress/save|delete`、`answer/add`、`goods/favor`）只尝试一次，
  避免"重试 = 重复下单/重复评价"这类生产事故
- 每次尝试都记录耗时与失败原因，日志与报告里能完整看到重试过程

### 3. 统一 Token 鉴权封装
- 接口对象只声明 `auth_type`（NONE / USER / ADMIN），token 注入由框架完成
- 会话级缓存：一次登录全程复用（专门写了用例 `test_token_is_cached_and_reused` 守护这件事，
  通过统计 `TokenManager.login_times()` 不变来断言"没有重复登录"）
- 失效自愈：业务码 -400 → 自动 `invalidate` + 重新登录 + 重试一次（额外给一次尝试机会）
- 线程安全：`RLock`；懒加载导入 `api_objects` 避免 core ↔ api_objects 循环依赖
- 脱敏：日志/附件里 token 显示为 `c2021a***3624`
- **负向能力**：调用方显式传入 `token` 时框架不覆盖（例如伪造 token / 无 token 的鉴权拦截用例）

### 4. DDT 数据驱动 + 缺陷守护用例
- 8 个数据集，`load_cases(file, group)` + `build_params()` 自动参数化，用例 ID 可读（`01-正向-正确账号密码登录成功`）
- `expected_code: "not_0"` 支持"只要求失败"的柔性断言（提示语不稳定时用）
- `known_defect` 字段 → 自动 `pytest.mark.xfail(reason=缺陷单号)`：
  **缺陷存在时报告为 xfail（不算失败），缺陷修复后变 XPASS，提醒你移除标记**——把"已知问题"变成可跟踪资产

### 5. 统一断言 + JSON Schema 契约校验
`Assert.success/fail/code/msg_contains/msg_equals/has_fields/schema/money/pagination/contains_keyword`
- 失败信息自带接口 `msg`（例："业务码不符：期望 code=0，实际 -9998，msg=响应非 JSON"）
- `Assert.money` 用容差比较，规避浮点误差（金额 0.1×2 这类场景）
- `Assert.schema` 用 jsonschema 做响应结构契约校验，字段缺失/类型错误立刻暴露（未装 jsonschema 自动跳过）

### 6. 环境能力探测 + 自动跳过（**最能体现测试思维的一条**）
现实问题：同一套框架要跑在多个环境，插件装没装、后台开不开都不一样。
做法：会话前探测能力 → `@pytest.mark.requires("coupon")` 的用例自动 skip 并写明原因
（`应用未安装[coupon]` / `后台入口被禁用（返回：非法访问）`）。
- **为什么重要**：不这样做，要么"假绿"（用 try/except 吞掉失败，等于没测），
  要么大面积报错把人淹没。我的选择是：**跳过要跳得明明白白，报告里能回答"为什么没跑"**
- 另留 `SHOPXO_FORCE_FEATURES=1` 逃生开关：怀疑探测误判时可强制执行被门控用例

### 7. 可观测性
- 结构化日志：`POST api/cart/save -> code=0 msg=加入成功 (耗时65.9ms, 第1/1次)`（控制台 INFO + 文件 DEBUG 滚动）
- Allure 附件：**可复现的 curl + 完整响应体**，失败用例直接复制 curl 就能复现
- 环境能力矩阵写入 Allure `environment.properties` 与 `reports/env_probe.json`
- 失败自动分类：`categories.json`（产品缺陷 / 环境问题 / 用例问题）
- 非 JSON 响应不抛裸异常，统一转框架错误码（-9998 非 JSON、-9999 网络），保留 `_raw`、`_http_status`

### 8. 测试数据自动清理（共享环境稳定性的关键）
测试环境是多人共用的沙箱（账号里有 230 笔订单、178 个地址），所以：
- 测试数据统一前缀 + 时间戳 + 随机串（`AutoTest0911xxxx`），互不干扰
- fixture 负责回收：`clean_cart`（前后各清一次购物车）、`temp_address`（teardown 删地址）、
  `temp_order`（先取消再删除）；用例内创建的数据在 `finally` 里清理
- **断开言不依赖全局总数**（不写 `total == 1`），只断言自己创建的数据与业务规则
- 效果：用例可**重复执行**，不会越跑越脏

### 9. 结果归档与质量看板（自己写插件 + 自包含看板）
- **痛点**：pytest-html 每次都覆盖 `reports/report.html`，历史结果留不下来，
  于是"这次回归比上次好还是差"根本回答不了；Allure 虽然好看，但要装 Java + Allure 命令行才能看。
- **做法**：写了一个 pytest 插件（`core/report_plugin.py`）在会话结束时采集**结构化结果**
  （用例、模块 marker、结论、耗时、跳过原因、缺陷单号），按运行编号归档到 `reports/history/<run_id>/`，
  再渲染成**自包含单文件看板** `reports/dashboard.html`：
  - 概览（通过率 / **可执行通过率**）、质量趋势（内联 SVG 折线 + 失败柱）、模块覆盖、
  - **缺陷看板**：由 xfail 守护用例自动汇总，缺陷修好后自动变成"已修复（可移除 xfail 标记）"，
  - 失败与跳过诊断（产品缺陷 / 环境问题 / 用例问题 / 跳过四类分开）、环境能力矩阵、可搜索的用例明细。
- **为什么是自包含 HTML**：零 CDN、零依赖，离线双击即开，能直接甩给开发/Leader；
  图表用内联 SVG 手写，交互用几十行原生 JS，页面里**不出现任何外部资源引用**——
  这条底线由 `tests/test_report_tools.py` 断言守护。
- **数据不能"说谎"**：看板页脚展示**数据自检**结论（分类合计=总数、明细条数一致、跳过必须写原因），
  归档/渲染失败只打印提示、绝不影响测试结论。
- **顺带解决了什么**：报告可追溯（每次执行一份快照）、趋势可对比、缺陷可跟踪、CI 产物可归档。

## 六、测试设计：三类用例 + E2E 闭环

| 类型 | 设计思路 | 例子 |
| --- | --- | --- |
| 正向 | 验证主流程与数据一致性 | 加购成功、订单确认页金额 = 购物车小计、多规格商品价格落在价格区间内 |
| 边界 | 参数极值、分页、长度 | 数量 0/-1、超页码、200 字符关键字/密码、金额浮点比较 |
| 异常 | 参数缺失/非法/业务规则拦截 | 商品不存在、支付方式非法、待付款订单不能删除/不能收货 |
| 安全 | 注入与越权 | SQL 注入式账号、伪造 token、缺失 token、XSS 关键字 |
| E2E | 跨模块链路 + 数据一致性 | 登录→搜索→详情→加购→改数量→确认→提交→详情→购物车校验→取消 |

**E2E 为什么要做**：单接口用例只能证明"某个接口返回值没变"，
而真实业务是跨模块的——搜索到的商品能不能加购？加购金额和订单金额对不对得上？
下单后购物车有没有清空？这些只有把链路串起来才能暴露。这条 E2E 共 11 步，**每步都断言**，
任何一环断裂都能定位到具体步骤。

**一个具体例子（体现数据一致性思维）**：
`test_order_confirm_amount_matches_cart`：加购 2 件 → 确认订单页 `base.total_price`
必须等于购物车 `total_price`，`goods_count` 必须等于商品种类数。
做这个用例时我发现 `goods_count` 的真实语义是**商品种类数（行数）而不是件数**，
于是把断言改成真实语义并加注释——**不断言"我以为的"，只断言"实际是对的"**。

## 七、发现的 7 个真实缺陷（面试最大加分项）

> 讲法：先说"怎么发现的"（用例设计/边界思维），再说"影响是什么"（业务风险），
> 最后说"我怎么跟踪的"（缺陷单号 + xfail 守护用例 + 复现证据）。

| 缺陷单 | 现象 | 风险 | 发现方式 |
| --- | --- | --- | --- |
| BUG-CART-STOCK-001 | 加购不校验库存上限，`stock=999999` 也返回"加入成功"，防线只在下单时生效 | 超卖、恶意占库存 | 边界值设计：故意传超过库存的数量 |
| BUG-ORDER-FILTER-001 | 订单列表 `status` 筛选完全失效，取 -1/0~6 返回同一份数据（total 恒 230），结果里还有与条件不符的状态 | 前端"待付款/已取消"筛选形同虚设 | 接口参数组合遍历 + 结果与条件一致性断言 |
| BUG-ORDER-COMMENT-001 | 待付款订单调评价接口返回 `code=0 提交成功`，但订单 `is_comments` 仍为 0 | 静默失败：用户以为评价成功，实际没落库 | 状态机 + 写后读校验（before/after 对比） |
| BUG-GOODS-SPEC-001 | `spec` 传畸形嵌套结构时服务端直接 HTTP 500（非 JSON） | 参数校验缺失，可被构造请求打崩（可用性风险） | 异常/非法结构输入测试 |
| BUG-ADDR-TEL-001 | 地址手机号不校验格式（`tel=abc` 新增成功），而留言接口同字段会拦截 | 脏数据、校验不一致 | 等价类划分（非法手机号） |
| BUG-ADDR-DETAIL-001 | 地址详情无存在性校验，不存在的 ID 返回 code=0 | 越权探测、信息泄露风险 | 异常 ID 输入 |
| BUG-ANSWER-TEL-001 | 留言接口对空字符串电话放行（`tel=''` 提交成功），字段完全缺失才拦截 | 校验逻辑不一致 | 空值 vs 缺值的差异测试 |

**"空字符串 vs 字段缺失"这个点特别值得讲**：同一个字段，缺失被拦截、空串被放行，
说明后端用的是 `isset` 而不是 `empty`（或校验顺序有问题）——这是典型的**校验逻辑不一致缺陷**，
只有把"缺失/空串/null/超长/特殊字符"都覆盖到才能发现。

## 八、CI/CD 集成

`Jenkinsfile`（声明式流水线，可直接用）：
- **触发**：代码提交自动触发 + **工作日每天 02:00 定时回归** + 手动传参
- **参数**：`BASE_URL`（环境）、`MARKER`（regression/smoke/p0/e2e）、`WORKERS`（并发）、`RERUN`、`GENERATE_ALLURE`

本地等价命令：`python run.py -m regression -n 4 --rerun 1 --allure-report`

## 九、诚实的边界（被问到必须这么答，别硬撑）

1. **优惠券（7 条）、商家后台（5 条）共 12 条用例在公开沙箱被跳过**：
   实测 `api/plugins/index?pluginsname=coupon` 返回 `code=-10 应用未安装[coupon]`，
   `admin.php?s=/admin/login/index` 返回 HTML「非法访问」。
   **代码、数据集、用例都已按插件分发入口与后台会话鉴权规范实现，
   换到装了插件、开放后台的环境（预发/本地部署）加一个 `--base-url` 就能执行。**
   我用 `SHOPXO_FORCE_FEATURES=1` 强制跑过这两个模块验证过代码路径是通的
   （失败原因是"插件未安装/入口被禁用"这种业务原因，不是框架报错），
   并顺带修掉了一个隐患：原本缺 `coupon_api`/`admin_api` fixture，在本环境被跳过掩盖，换环境就会报错。
2. **在线支付链路无法验证**：沙箱只提供"货到付款"一种支付方式，所以只能验证
   "不支持的支付方式不会被误判成功"，无法验证支付成功后的状态流转。
3. **Jenkins 没有实际跑过构建**：流水线文件已按标准写好，并用本地等价命令
   （`run.py -m regression -n 4 --rerun 1 --allure-report`）验证过执行链路；
   公司有 Jenkins 的话接入只需配置任务指向仓库。
4. **Allure 命令行未安装**：`allure-pytest` 已接入并产出 `allure-results` 原始数据，
   生成 HTML 需要额外的 Allure CLI（Java 环境已具备）。
5. **速度数据**：全量 284 条约 30 秒（单进程，串行发起网络请求），支持 `-n 4` 并行；
   其中 186 条框架离线自测 1.3 秒跑完，适合放进 PR 门禁。
6. **公开沙箱的测试账号被改过密码**：项目依赖的账号中途失效（接口返回 `code=-4 密码错误`），
   当时报告里出现 25 个失败 + 53 个跳过，看上去像代码或用例出了问题。我做了三件事：
   ①写 `tools/check_login.py` 凭证预检，跑测试前先确认账号可用（也可作 CI 前置卡点）；
   ②数据文件改用 `${USER}`/`${PWD}` 占位符，账号密码只在配置/环境变量里维护一处；
   ③把免登录接口（搜索、商品详情）的鉴权声明从 `USER` 改成 `NONE`，
   让账号失效时的影响面收敛到真正依赖登录的用例——否则搜索、商品这类不依赖登录的用例会被误报成失败。
   **这是"环境问题"与"产品缺陷/用例缺陷"分离的真实案例**，也说明自动化框架必须能定位根因，
   而不是让所有用例一起变红。

## 十、面试问答库

### A. 项目类

**Q1：你这个项目做了什么？**
见"一分钟版本"。要点：分层框架 + 数据驱动 + 环境自适应 + CI 接入 + 7 个真实缺陷。

**Q2：为什么要分层？脚本能跑不就行了吗？**
脚本的寿命通常只有一次迭代。分层解决三个成本：
①接口变更成本（只改 `api_objects`，我在 404 路由问题上验证过，改 1 处、10 条用例零改动）；
②数据变更成本（用例数据外置 JSON，加边界用例不改代码）；
③环境变更成本（配置全走环境变量，加 `--base-url` 就换环境）。
另外分层后**框架能力可以复用**：重试、鉴权、断言、报告只写一次，所有模块共享。

**Q3：为什么用 Pytest 而不是 unittest/Postman？**
Pytest 的 fixture（依赖注入 + 分层 setup/teardown）、参数化、marker 分组、插件生态
（allure-pytest/xdist/rerunfailures/html）正好覆盖自动化框架需要的全部能力；
unittest 需要自己造这些轮子。Postman 适合接口调试和少量冒烟，
但无法承载"数据驱动 + 自动清理 + CI 卡点 + 报告归档"这套工程化诉求。

**Q4：项目里最有技术含量/最难的部分是什么？**
统一鉴权 + 请求重试的幂等保护 + 环境自适应跳过。
难在"要在正确性（不重复下单）、稳定性（偶发失败能自愈）、真实性（不掩盖问题）之间取舍"。

**Q5：你从这个项目里最大的收获？**
**测试的价值在于发现问题，而不是让报告变绿。** 我一开始也差点把"跳过/吞异常"当解决方案，
后来改成"能力不足就明确跳过并说明原因"，同时把 7 个缺陷做成 xfail 守护用例——
报告里 265 绿、12 明确跳过、7 个缺陷可见，比 284 全绿但什么都没证明要诚实得多。

### B. 框架/技术类

**Q6：重试会不会导致重复下单？**
**不会，这是设计时就防住的**：重试策略和幂等性绑定。
`BaseAPI.request()` 有 `idempotent` 参数，下单（`buy/add`）、支付（`order/pay`）、
评价（`order/comments`）等写操作显式传 `idempotent=False`，此时 `attempts = 1`，
连网络异常也不重试（宁可失败让人看到，也不能产生脏数据）。

**Q7：Token 怎么管的？为什么不用每个用例都登录？**
`TokenManager` 进程级缓存：首次调用时登录并缓存，后续直接复用；
`RLock` 保证并发（xdist/多线程）下不会重复登录；业务码 -400 时自动失效重登并重试一次。
我还专门写了用例守护这个行为——统计 `login_times()` 在多次调用前后不变。
收益：284 条用例只登录 1 次，既快又避免账号被风控。

**Q8：token 放在 header 还是参数？**
按**接口文档**来：ShopXO 文档规定 token 通过 GET 参数传递，所以框架统一注入到 `params`；
调用方显式传了 token 就不覆盖（这样我才能写"伪造 token / 无 token"的鉴权负向用例）。

**Q9：接口返回不是 JSON（比如 500 错误页）你怎么处理？**
不抛裸异常，统一转成框架错误码：`-9998`（响应非 JSON）+ 保留 `_raw`、`_http_status`，
断言失败信息里就能看到"HTTP 500、返回 HTML"。这样断言逻辑统一，排查也快。
（这个设计后来真的用上了——BUG-GOODS-SPEC-001 就是靠它暴露出来的。）

**Q10：数据驱动怎么做的？**
`data/*.json` 存用例数据，`load_cases()` 加载（支持 `group` 分场景），
`build_params()` 生成 `pytest.param`（自动把 `known_defect` 的用例打成 xfail），
`case_ids()` 生成可读用例 ID。用例侧一行：
`@pytest.mark.parametrize("case", build_params(load_cases("cart_data.json", group="add")), ids=...)`

**Q11：什么是 JSON Schema 契约校验？为什么需要？**
用 `data/schemas/*.json` 描述响应结构（必填字段、类型），`Assert.schema()` 调用 jsonschema 校验。
它和业务断言互补：业务断言验证"值对不对"，schema 验证"结构有没有变"——
后端少返回一个字段、类型从 string 变 int，业务断言可能仍通过，schema 会立刻报出来。

**Q12：Allure 是怎么接入的？**
三层：①`run.py` 检测到 `allure-pytest` 就自动加 `--alluredir`（**依赖缺失自动降级**，不阻断执行）；
②`core/allure_utils.py` 做适配层，`@step`/`attach_text`/`attach_json` 在未安装 Allure 时是空操作；
③`BaseAPI` 每次请求把**可复现的 curl + 完整响应**挂成附件，conftest 把环境能力写进
`environment.properties`、失败分类写进 `categories.json`。

**Q13：为什么要有 `env_check.py`？**
因为环境差异会毁掉自动化：插件没装、后台关了、某个路由 404。
探测一次（缓存），驱动 `pytest_collection_modifyitems` 自动跳过，把"为什么没跑"写进报告。
比起"每条用例自己 try 一下再 skip"，这样更集中、更快，也不会漏。

### C. 测试设计类

**Q14：你怎么保证用例可重复执行（不越跑越脏）？**
①数据唯一化（前缀+时间戳+随机串）；②fixture 自动回收（购物车/地址/订单）；
③**断言不依赖全局总数**，只断言自己的数据；④幂等设计（收藏用例 toggle 两次自动还原）。

**Q15：共享测试环境数据被别人改坏怎么办？**
确实遇到过（沙箱账号里有 230 笔订单、178 个地址）。做法：
不假设"环境是干净的"，用例只操作自己创建的数据；关键数据（商品）用预检脚本
`check_goods_status.py` 提前校验；`SHOPXO_GOODS_ID` 可通过环境变量替换。

**Q16：边界用例你是怎么设计的？**
从参数维度拆：数值（0/负/超大/超库存）、字符串（空/超长/特殊字符/SQL 注入/XSS）、
分页（超页码/第 2 页/空结果）、状态（待付款/已取消分别能做什么）、
字段存在性（缺失 / 空串 / null）。"缺失 vs 空串"就是这么发现的 BUG-ANSWER-TEL-001。

**Q17：怎么判断一个接口"测完了"？**
我的标准：正向链路通 + 参数边界全覆盖 + 业务规则拦截验证 + 响应结构契约 + 鉴权校验 +
跨接口数据一致性（如订单金额=购物车小计）。缺一项都算没测完。

**Q18：断言失败信息怎么设计才算好？**
带上下文：期望值、实际值、接口 `msg`、用例描述。
例如"业务码不符：期望 code=0，实际 -9998，msg=响应非 JSON（HTTP 500）"——
不用翻日志就知道是环境问题还是产品问题。

**Q19：E2E 用例应该覆盖多少？**
不追求多，追求"链路关键节点全覆盖"。我只写 1 条，
但把 11 个步骤（登录→搜索→详情→加购→改数量→确认→提交→详情→购物车校验→取消→清理）
每步都断言，投入产出比最高。

**Q20：被测系统状态机你怎么测的？**
先摸清状态语义（实测：1 待付款、5 已取消），再枚举"每个状态下能做什么/不能做什么"：
待付款 → 可取消、不可删除、不可收货；已取消 → 可删除、不可再取消；删除后 → 不可再删除。
每个非法操作都断言被拦截且提示正确（`状态不可操作[待付款]`、`资源不存在或已被删除`）。

### D. 陷阱题（重点准备）

**Q21：你有 12 条用例是跳过的，覆盖率怎么算？**
不把跳过的算成通过。口径分两层：
**可执行覆盖**=92+7 条在当前环境有明确结论（7 条是"确认为缺陷"）；
**代码/数据集覆盖**=那 12 条对应的接口封装与用例都已实现，只是环境不具备执行条件，
跳过后报告里能看到具体原因。我不会把 skip 计入通过率来美化数字。

**Q22：7 个 xfail 是不是等于放着没管？**
不是。xfail 是**已知缺陷的守护用例**：每个都绑定缺陷单号（如 BUG-CART-STOCK-001），
带复现步骤与实测证据，并且**缺陷一旦修复，用例会变成 XPASS**，提醒我移除标记——
这样"已知问题"变成可跟踪资产，而不是被静默忽略。
如果团队确认某个现象是预期行为，我会把断言改成"记录真实行为 + 注释说明"，把它转为正向用例。

**Q23：你这些缺陷有没有真的提给开发？**
我整理成了缺陷清单（现象/复现步骤/风险/证据），但因为被测的是公开沙箱、没有对应的研发团队，
所以是以缺陷单形式归档在项目里 + 用 xfail 用例守护。
真实工作中我会走缺陷管理流程（Jira）+ 复测闭环。

**Q24：如果让你提高执行速度呢？**
当前全量约 30 秒已经很快。可做的：①`-n 4` 并行（已支持，但要给每个 worker 分配独立账号避免互相干扰）；
②把只读校验类用例合并；③给登录加 session 级复用（已做）。
但**速度不是第一优先级**，稳定性和失败可定位性更重要。

**Q25：测试用例越多越好吗？**
不是。我按"价值密度"取舍：核心链路（登录/加购/下单）覆盖到边界与异常，
边缘接口保证正反向即可。我宁可 284 条每条都有明确目的，也不要 300 条重复用例。

**Q26：你这套框架能直接用在别的项目上吗？**
能，`core/` 与 `config/` 是通用的，只需换 `api_objects/`（路由与参数）+ `data/`（数据与 schema）
+ 调整 `env_check` 的能力项。这也是我坚持分层的直接目的。

### E. 场景题

**Q27：接口加了新参数，你怎么改？**
接口层方法加参数（带默认值，兼容旧用例）→ 数据集里加新用例 → 跑测试。
不涉及用例层改动，这是分层的价值。

**Q28：CI 上偶发失败（比如网络抖动）怎么处理？**
三层：①框架层重试（幂等接口，退避策略）；②CI 层 `--rerun 1`（pytest-rerunfailures）；
③定位层——重试过程与失败响应都在日志/Allure 里，先判断是环境抖动还是真实缺陷，
**不允许用重跑掩盖真实问题**（非幂等接口禁用重试就是这条原则的体现）。

**Q29：怎么测一个"优惠券满减"的业务？**
（当前环境跑不了，但可以讲思路）正向：领券→下单用券→订单金额=原价-券额；
边界：刚好等于门槛/差 0.01/超过门槛、券过期、多张券叠加；
异常：未登录领券、重复领同一张、用别人的券 ID（越权）、券不适用该商品；
数据一致性：券状态从"未使用"到"已使用"、订单取消后券是否退回。

**Q30：如果测试环境和生产不一致导致用例失败，怎么办？**
先区分"用例问题"还是"环境问题"：断言失败信息 + 日志 + curl 复现三步定位。
如果是环境差异（如商品数据不同），用环境变量/数据文件参数化，而不是改断言迁就环境；
如果是环境本身有问题（如插件没装），走能力探测跳过并记录原因。

**Q31：测试报告每次执行都被覆盖、历史结果留不下来，你们怎么解决的？**
（这题是我自己踩过的坑）老做法是 `pytest --html=reports/report.html`，跑一次覆盖一次，
于是"这次回归比上次好还是差""缺陷有没有收敛"都答不了。我的做法是写一个 pytest 插件
（`core/report_plugin.py`）在会话结束时采集**结构化结果**，按运行编号归档到
`reports/history/<运行编号>/`（report.html + summary.json + dashboard.html），默认保留最近 50 次、自动裁剪；
再渲染一个**自包含单文件看板** `reports/dashboard.html`（零 CDN、离线双击即开）：通过率趋势、
**与上次对比**（新增失败 / 已修复 / 新增跳过 / 新增用例 / 持续失败）、**不稳定用例 flaky Top N**、
模块覆盖、缺陷看板（xfail 修好后自动显示"已修复"）、失败与跳过诊断、
环境能力矩阵、可搜索的用例明细。两个细节体现严谨：看板页脚会做**数据自检**
（分类合计=总数、明细条数一致、跳过必须写原因）；看板本身也有单测
（`tests/test_report_tools.py`，22 条），其中一条断言"页面不得出现任何外部资源引用"，
保证离线场景下不会打不开。

**Q32：框架自身怎么保证质量？CI 是怎么落地的？**
只测被测系统是不够的——框架吞异常、重试带旧 token、脱敏漏了响应体，业务用例照样是绿的。
所以我做了双轨：`tests/unit/**` 用 `responses` 把 HTTP 全部 mock 掉，专门断言**框架自己的行为**
（重试次数与退避、非 JSON/超时容错、幂等开关、token 缓存与失效重登、脱敏、占位符展开、看板渲染），
0 网络依赖。第一版离线套件就抓出 **9 个框架缺陷**：

- `-400` 失效重登是**假的**：`invalidate()` 清了缓存，但重试复用同一份 `params`，
  `_inject_token()` 见到已有 token 直接返回 → 重试仍发旧 token，日志却写"已重新登录并重试"；
- 登录**响应体**未脱敏：`data.token` 明文进 `last_exchange`，并作为 Allure 附件落盘；
- `pwd` 长度 ≤3 时不脱敏；`load_cases(group=...)` 分组名拼错时静默返回**全部**用例；
  `unique()` 截断把随机后缀整体砍掉（返回值退化成常量）；`CODE_NETWORK`(-9999) 文档与代码口径分裂；
  环境探测把"探测失败"当成"能力可用"；探测异常只留类名不留原因；`note` 等说明字段也被替换进凭据。

这 9 个都已修复，并把守护用例从"xfail 记录现状"改成"断言修复后行为"——
**发现问题 → 登记 → 修复 → 用测试锁死**这条链路才是完整的。
CI 上（`.github/workflows/api-test.yml`）分两档：PR 跑**离线门禁**（186 条、1.3 秒、
`--cov=core` 覆盖率红线 78%，并上传看板/摘要/历史归档等产物），定时任务才跑真实环境回归
（先用 `tools/check_login.py` 做账号预检，环境不可用就跳过，而不是把仓库卡红）。

## 十一、回答时的三个原则

1. **数字要准**：284 条用例（98 真实环境 + 186 离线自测）/ 265 passed / 12 skipped / 7 xfailed / 0 failed /
   约 30 秒（离线 1.3 秒）/ 业务缺陷 7 个 + 框架缺陷 9 个（已修复）/ 30 个接口 / core 覆盖率 80%。
2. **边界要主动说**：优惠券和商家后台在公开沙箱跑不了（插件未安装、后台被禁），
   我选择明确跳过而不是假绿——**主动说边界比被问出来强**，而且这本身就是测试思维的体现。
3. **有取舍才有说服力**：每个设计都配一个"为什么这么做 + 不这么做会怎样"
   （重试 vs 重复下单、跳过 vs 假绿、断言真实语义 vs 断言我以为的语义）。
