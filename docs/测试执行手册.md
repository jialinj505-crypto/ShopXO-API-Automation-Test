## 1. 准备 Python 环境

### 1.1 情况 A：环境已就绪（本机现状，推荐）

项目里已经有可用的虚拟环境 `.venv`（Python 3.11.7，已装好 pytest / requests / allure-pytest / pytest-html / jsonschema）。
只需确认依赖是齐全的：

```powershell
cd C:\PycharmProjects\MyTestProject
.\.venv\Scripts\python.exe -V
.\.venv\Scripts\python.exe -m pip list | Select-String "pytest|allure|jsonschema|requests"
```

期望看到：`pytest 9.1.1`、`pytest-html 4.2.0`、`allure-pytest 2.16.0`、`jsonschema 4.19.2`、`requests 2.34.2`、`pytest-xdist 3.8.0`、`pytest-rerunfailures 16.4`。

### 1.2 情况 B：换一台电脑 / 想完全从零重建

> ⚠️ **踩坑警告（本机真实发生过）**：不要对**已存在**的 `.venv` 再执行一次 `python -m venv .venv`。
> venv 会重写 `.venv\pyvenv.cfg`，把 `include-system-site-packages` 重置为 `false`，
> 导致 pytest/requests/jsonschema 等**依赖瞬间不可见**（报 `No module named pytest`）。
> 要重建就**先删除整个 `.venv` 目录**，再按下面步骤操作。

```powershell
cd C:\PycharmProjects\MyTestProject

# 0) 若已存在旧环境，先删干净（否则会被重写成半残状态）
Remove-Item .venv -Recurse -Force

# 1) 用 Anaconda 的解释器创建虚拟环境（-m venv 不要写成 virtualenv）
C:\ProgramData\anaconda3\python.exe -m venv .venv

# 2) 升级 pip 并安装依赖（这一步不能省：venv 是独立的，不会自动看到 Anaconda 里的包）
.\.venv\Scripts\python.exe -m pip install -U pip
.\.venv\Scripts\python.exe -m pip install -r requirements.txt

# 3) 校验（下面每一项都应为 True，pytest 应能打印版本号）
.\.venv\Scripts\python.exe -c "import importlib.util as u; [print(m, u.find_spec(m) is not None) for m in ['pytest','requests','jsonschema','pytest_html','allure_pytest','xdist']]"
.\.venv\Scripts\python.exe -m pytest --version
```

**关于 conda 环境（`(sb_env)` 这类前缀）**：终端里激活的 conda 环境**不影响本项目**。
我们所有命令都用 `.venv\Scripts\python.exe` 这个绝对路径调用解释器，
跟 `python`/`pip` 命令解析到哪个 conda 环境无关，**不需要切环境，也不需要 `conda deactivate`**。
（反过来说：如果你图省事敲了裸 `python -m pytest`，那它用的就是 conda 环境 / Store 占位程序，
缺依赖报错是正常的——请始终带上解释器路径。）

如果想在命令行激活虚拟环境（可选，不激活也能用，因为我们是直接调用 exe）：

```powershell
# PowerShell（若提示“禁止运行脚本”，改用下一行的 cmd 方式）
.\.venv\Scripts\Activate.ps1
# cmd
.\.venv\Scripts\activate.bat
```

## 4. 执行测试（按需选择）

> 统一入口 `run.py` 会自动附加参数：装了 `allure-pytest` 就产出 `reports/allure-results`，
> 装了 `pytest-html` 就产出 `reports/report.html`，并透传其余参数给 pytest。

### 4.1 全量回归（最常用，约 30 秒）

```powershell
.\.venv\Scripts\python.exe run.py
```

### 4.2 冒烟（提交代码前的快速校验，5 条）

```powershell
.\.venv\Scripts\python.exe run.py -m smoke
```

### 4.3 核心链路 P0

```powershell
.\.venv\Scripts\python.exe run.py -m p0
```

### 4.4 只要 E2E 闭环（登录→搜索→加购→下单→取消）

```powershell
.\.venv\Scripts\python.exe run.py -m e2e
```

### 4.5 并行加速 / 失败重跑（大批量回归时用）

```powershell
.\.venv\Scripts\python.exe run.py -n 4                 # 4 进程并行（xdist）
.\.venv\Scripts\python.exe run.py --rerun 1            # 失败用例重跑 1 次
.\.venv\Scripts\python.exe run.py -m regression -n 4 --rerun 1 --allure-report   # 模拟 CI
```

### 4.6 切换被测环境（换域名 / 本地部署的 ShopXO）

```powershell
.\.venv\Scripts\python.exe run.py --base-url http://127.0.0.1

$env:SHOPXO_BASE_URL = "http://127.0.0.1"
$env:SHOPXO_USER = "你的账号"; $env:SHOPXO_PWD = "你的密码"
.\.venv\Scripts\python.exe run.py
```

### 4.7 单模块 / 单个用例（调试用）

```powershell
# 整个模块，显示每条用例名
.\.venv\Scripts\python.exe -m pytest tests\test_order.py -v

# 按名称关键字筛选（中文可用）
.\.venv\Scripts\python.exe -m pytest tests\test_cart.py -k "超库存" -v

# 单个用例，打印完整请求日志
.\.venv\Scripts\python.exe -m pytest "tests\test_order_e2e.py::test_shopping_flow_end_to_end" -vv -s

# 只看失败用例 + 简短回溯
.\.venv\Scripts\python.exe -m pytest -q --tb=short -rf
```

### 4.8 控制台中文乱码时

```powershell
$env:PYTHONUTF8 = '1'; [Console]::OutputEncoding = [System.Text.Encoding]::UTF8
```

### 4.9 只跑框架离线自测（0 网络依赖，约 1.3 秒）

框架自身也会有 bug（重试次数写错、异常被吞、token 未脱敏、占位符没替换），
所以 `tests/unit/**` 加报告工具自测共 **186 条**用例，用 `responses` 把 HTTP 全部 mock 掉，
专门验证框架逻辑，全程不访问任何网络：

```powershell
.\.venv\Scripts\python.exe run.py --offline            # 只跑离线自测（标签默认 offline）
.\.venv\Scripts\python.exe run.py --offline --tag pr-gate

# 框架覆盖率（与 CI 门禁同款命令：当前门槛 78%，实测 80%）
$env:SHOPXO_OFFLINE='1'
.\.venv\Scripts\python.exe -m pytest -m offline --cov=core --cov-report=term-missing
```

> 离线模式会把环境能力探测短路（不探真实环境），因此看板里的能力矩阵显示"未探测"，
> 而不是伪造成"不支持"——**离线报告不编造真实环境结论**。

## 5. 查看与解读报告

| 产物 | 位置 | 说明 |
| --- | --- | --- |
| **质量看板** | `reports\dashboard.html` | **推荐先看这个**：概览、趋势、模块覆盖、缺陷看板、失败诊断、能力矩阵、用例明细；自包含单文件，可离线打开、可直接发给别人 |
| HTML 报告 | `reports\report.html` | 本次 pytest-html 详细报告（Jenkins 归档用），单文件自带样式 |

| **历史归档** | `reports\history\<运行编号>\` | 每次执行一份快照：`report.html + summary.json + dashboard.html`，**历史结果不会被覆盖** |
| Allure 原始结果 | `reports\allure-results\` | 含用例层级、步骤、**请求 curl + 完整响应附件**、环境能力信息、失败分类（仅保留最近一次） |
| Allure HTML | `reports\allure-report\index.html` | 由 `run.py --allure-report` 生成；CLI 已装在项目内 `.tools\`（详见 5.1） |
| 执行日志 | `logs\autotest.log` | 全量请求/断言/数据清理记录，排查问题首选 |
| 环境能力矩阵 | `reports\env_probe.json` | 本次执行环境的探测结果（登录、路由、插件、后台） |

### 5.1 生成并查看 Allure 报告

Allure 分两段：`allure-pytest`（Python 插件，**已装**）负责产出原始结果 `reports\allure-results`；
官方 **allure 命令行**负责把原始结果渲染成 HTML（依赖 Java 8+，本机 `jdk1.8.0_341` 已实测可用）。

**CLI 已装在项目内 `.tools\allure-2.46.1`**，由 `run.py` 自动识别
（查找顺序：`ALLURE_HOME` → `.tools\allure-*` → 系统 PATH），因此**不需要改 PATH**。
换电脑或删掉 `.tools` 后，一条命令重装：

```powershell
.\.venv\Scripts\python.exe tools\get_allure.py            # 装最新版到项目内 .tools\
.\.venv\Scripts\python.exe tools\get_allure.py --check    # 只检查当前是否可用（含 Java 自检，退出码 0/1）
```

脚本优先走 **GitHub API 资产通道**下载（受限网络访问 `github.com` 会超时，而 `api.github.com` 可达），
下载后按 release 公布的 **sha256** 校验，最后执行 `allure --version` 自检 Java 环境——装不上会明确告诉你原因。

生成与查看：

```powershell
# 方式一（推荐）：执行回归并自动渲染 HTML
.\.venv\Scripts\python.exe run.py --allure-report
start reports\allure-report\index.html

# 方式二：基于已有原始结果临时起服务（不重新跑用例，改完报告即可刷新）
.\.tools\allure-2.46.1\bin\allure.bat serve reports\allure-results
```

**一个数字口径差异（被问到要能答）**：allure-pytest 把 pytest 的 `xfailed` 计入 `skipped`，
所以同一份结果 pytest 报「12 skipped + 7 xfailed」、Allure 报「19 skipped + 0 failed」，
两者总数都是 284 且都是 0 真实失败——是工具口径差异，不是数据不一致。

Allure 相关排错：

| 现象 | 原因与处理 |
| --- | --- |
| `[警告] 未找到 allure 命令行` | CLI 不在 `.tools\`：跑 `tools\get_allure.py`，或设 `ALLURE_HOME` 指向解压目录 |
| `allure --version` 报 Java 相关错误 | Allure 需要 Java 8+：检查 `java -version` 与 `JAVA_HOME` |
| 报告用例数比预期少 | `allure-results` 只保留最近一次执行（`--clean-alluredir`），先跑一次 `run.py` 再生成 |
| 报告样式丢失 | 打开 `reports\allure-report\index.html` 时要在该目录内打开（同一目录下有 data/widgets 资源），别单独拷走 index.html |

### 5.2 质量看板与历史归档（不需要装任何东西）

每次执行 `run.py` 都会自动做两件事，**不需要额外命令**：

1. 把本次结果按运行编号归档：`reports\history\<运行编号>\`（含 `report.html`、`summary.json`、`dashboard.html`）——
   **再也不会出现"上一次的报告被覆盖"的问题**；
2. 生成/刷新质量看板：`reports\dashboard.html`。

```powershell
# 直接打开看板（自包含单文件，双击也行）
start reports\dashboard.html
.\.venv\Scripts\python.exe run.py --open            # 或执行完自动打开

# 想区分不同范围的执行（趋势图上会显示标签）
.\.venv\Scripts\python.exe run.py --tag 发版前回归
```

看板上能直接回答这些问题：

| 问题 | 看板位置 |
| --- | --- |
| 这次能不能发版？ | 顶部结论 + 概览卡片（通过率 / 可执行通过率） |
| 比上次好还是差？ | 质量趋势（通过率折线 + 失败柱；横轴标注运行编号与用例总数）+ **与上次对比**（新增失败 / 已修复 / 新增跳过 / 新增用例 / 持续失败，同标签优先对比） |
| 有没有"时好时坏"的用例？ | **不稳定用例（flaky）Top N**：按历史归档统计同一用例的翻转比例（至少出现 2 次、既有成功也有失败；跳过不计入） |
| 哪些模块有风险？ | 模块覆盖（各模块通过/失败/跳过与耗时） |
| 已知缺陷还在吗？ | 缺陷看板（由 xfail 守护用例自动汇总，修复后自动变"已修复"） |
| 失败是产品问题还是环境问题？ | 失败与跳过诊断（产品缺陷 / 环境问题 / 用例问题 / 跳过） |
| 为什么有一批用例没跑？ | 环境能力矩阵 + 跳过原因（含具体实测依据） |
| 某条用例到底怎么失败的？ | 用例明细（可搜索/筛选，点击行展开说明），需要请求与响应细节时看 `report.html` 或 Allure |

> 看板只读消费 `summary.json`，不参与测试执行；页面底部还会显示**数据自检结论**
> （分类合计是否等于总数、明细条数是否一致、跳过是否写了原因）。
> 历史保留次数默认 50，可用 `--history-keep` 调整。

## 6. 结果判定标准（重要，别把「跳过」当成「失败」）

全量回归的**正常输出**是：

```
================= 265 passed, 12 skipped, 7 xfailed in 31.xx s =================

本次结果 : 总数 284 | 通过 265 | 失败 0 | 错误 0 | 跳过 12 | 缺陷守护 7 | 通过率 93.31%（可执行通过率 97.43%）
运行编号 : 20260916-154035
归档目录 : reports\history\20260916-154035（history/<运行编号>/，历史结果不会被覆盖）
质量看板 : reports\dashboard.html
```

| 状态 | 数量 | 含义 | 你需要做什么 |
| --- | --- | --- | --- |
| `passed` | 265 | 用例通过（真实环境 79 条 + 框架离线自测 186 条） | 无需处理 |
| `skipped` | 12 | **环境能力不足，主动跳过**（优惠券 7 条 + 商家后台 5 条） | 看 `reason`：`应用未安装[coupon]`、`后台入口被禁用（返回：非法访问）`。这是被测沙箱的限制，**不是用例失败**；换到装了插件/开放后台的环境会自动执行 |
| `xfailed` | 7 | **已登记缺陷，按预期失败** | 表示 7 个已知问题仍存在；若某条变成 `XPASS`，说明该缺陷被修复了，可以去 `data/*.json` 里移除 `known_defect` 标记 |
| `failed` | 0 | 就是一条都不该有 | 有 failed 时按第 7 节排查 |
| `error` | 0 | fixture / 环境初始化异常 | 通常是网络或登录问题，看 `logs\autotest.log` 开头 |

**7 个 xfail 对应的缺陷单**（详见 README 第七节）：
BUG-CART-STOCK-001、BUG-ORDER-FILTER-001、BUG-ORDER-COMMENT-001、BUG-GOODS-SPEC-001、
BUG-ADDR-TEL-001、BUG-ADDR-DETAIL-001、BUG-ANSWER-TEL-001。

## 7. 常见问题排查表

| 现象 | 原因 | 解决 |
| --- | --- | --- |
| `python : 无法将“python”项识别为...` 或弹出应用商店 | PATH 里的 python 是 Store 占位程序 | 改用 `.\.venv\Scripts\python.exe`（本手册全篇如此） |
| `No module named pytest` | 用错了解释器（用了系统 python） | 统一用 `.\.venv\Scripts\python.exe -m pytest` |
| `ApiError: ... 请求失败（已尝试 3 次）：ConnectionError` | 网络不通 / 沙箱不可达 | `curl http://shop-xo.hctestedu.com` 自测；或加大 `$env:SHOPXO_TIMEOUT=30` |
| 登录用例 `code=-4 密码错误` | 公开沙箱账号密码被他人修改或被重置（实测文档里的初始密码已失效，现为 `123456`） | 先跑 `python tools/check_login.py` 自检；确认后设置 `$env:SHOPXO_USER` / `$env:SHOPXO_PWD`，或更新 `config/setting.py` 默认值 |
| 加购/下单报「商品不存在或已删除」 | 默认商品下架了 | 跑 `tools\fetch_valid_goods.py` 抓新商品，再用 `$env:SHOPXO_GOODS_ID=新ID` |
| 订单/购物车用例大面积失败 | 共享沙箱账号里有别人的脏数据 | 用例本身会自清购物车；仍异常时手工清一次（先 `run.py -m smoke` 让 fixture 清理，或直接调 `cart/delete`） |
| `SKIPPED ... 不支持能力[coupon]` | 环境没装优惠券插件 | 正常现象；要跑就换环境（`--base-url`） |
| 怀疑能力探测误判 | 探测结果与实际不符 | `$env:SHOPXO_FORCE_FEATURES=1` 强制执行被门控用例，失败信息即为真实业务返回 |
| `allure: 无法将“allure”项识别为...` | 未安装 Allure 命令行 | 按 5.1 安装；或先看 `reports\report.html` |
| 报告里中文乱码 | 控制台编码 | `$env:PYTHONUTF8='1'` + `[Console]::OutputEncoding=[System.Text.Encoding]::UTF8` |
| `Access to the path '...\.pytest_cache' is denied` | 缓存目录权限异常（残留） | 删除该目录：`Remove-Item .pytest_cache -Recurse -Force`，或 `-p no:cacheprovider` 跳过缓存 |
| 想看"上一次"的报告，但 `reports\report.html` 已经被覆盖 | 老版本只保留最新一份 | 现在每次执行都会归档到 `reports\history\<运行编号>\`（含 report.html + summary.json + dashboard.html），趋势对比直接看 `reports\dashboard.html` |
| 看板打不开 / 图表不显示 | 页面依赖了外部资源（网络不可用） | 本项目的看板是**自包含单文件**（内联 CSS/JS/SVG，0 处外部引用），已由 `tests/test_report_tools.py` 守护；如仍异常，先用浏览器打开 `reports\report.html` 兜底 |
| `run.py --offline` 显示"未探测真实环境" | 离线模式的**设计行为**：不访问网络，也不假装探测过 | 想看真实环境结论就跑全量或 `-m smoke` |
| CI 报 `Coverage failure: total of 80 is less than fail-under=78` | 新增的框架代码没有对应单测 | 在 `tests/unit/` 补用例；本地先跑 `pytest -m offline --cov=core --cov-report=term-missing` |
| CI 的 `sandbox-smoke` 显示跳过 | 真实环境回归前会先跑 `tools/check_login.py` 预检 | 预检失败（沙箱账号被改 / 不可达）时跳过而不卡红仓库；确认后用 `$env:SHOPXO_USER/$env:SHOPXO_PWD` 覆盖 |
| `无法加载文件 ...\init_git.ps1，因为在此系统上禁止运行脚本` | Windows 默认执行策略为 Restricted | 加 `-ExecutionPolicy Bypass`：`powershell -ExecutionPolicy Bypass -File tools\init_git.ps1`；或临时 `Set-ExecutionPolicy -Scope Process Bypass` |
| 看板"与上次对比"显示"无可比历史" | 历史归档里没有同标签的运行 | 至少跑两次（建议用 `--tag` 固定标签，如 `--tag 回归`），对比会优先选取同标签的上一次执行 |

## 8. 测试数据卫生（每次执行前后）

## 9. 接入 CI/CD（GitHub Actions + Jenkins）

### 9.1 GitHub Actions（仓库自带：`.github/workflows/api-test.yml`）

| 任务 | 触发 | 内容 |
| --- | --- | --- |
| `offline-framework-check` | 每次 push / PR | `SHOPXO_OFFLINE=1` 跑 186 条框架离线自测（约 1.3 秒，0 网络依赖）+
 `--cov=core --cov-fail-under=78` 覆盖率门禁；上传看板、结构化结果、历史归档、覆盖率 XML 与日志，摘要写进 Step Summary |
| `sandbox-smoke` | 工作日定时 + 手动 | 真实环境冒烟：先 `tools/check_login.py` 预检（不可用则跳过），再 `run.py -m smoke --tag CI-smoke`，归档看板与报告 |

> 为什么 PR 只跑离线：秒级、稳定、不受共享沙箱被别人改密码 / 下架商品的影响；
> 真正依赖环境的回归放到定时任务，并用预检把"环境不可用"和"代码有问题"区分开。

徽章：README 顶部徽章已指向本仓库（`https://github.com/jialinj505-crypto/ShopXO-API-Automation-Test`），
推送到该仓库后 Actions 首次运行完即显示构建状态。

### 9.2 Jenkins

1. 先把代码提交到 Git 仓库（本机未安装 git，需先装：
   `winget install --id Git.Git` 或 https://git-scm.com/download/win ）。
   仓库初始化 + 规范提交历史可以一条命令完成（脚本在缺少 git 时会给出安装提示并退出，
   不会"提交一半"；重复执行也安全）：

   ```powershell
   cd C:\PycharmProjects\MyTestProject
   powershell -ExecutionPolicy Bypass -File tools\init_git.ps1
   git remote add origin https://github.com/jialinj505-crypto/ShopXO-API-Automation-Test.git
   git push -u origin main
   ```

   > 若本机没配过用户名/邮箱，脚本会用占位值（`ShopXO QA <qa@example.com>`）；
   > 推到自己的仓库前建议先 `git config user.name / user.email` 改成真实信息。

2. Jenkins 新建 `Pipeline` 任务 → `Pipeline script from SCM` → 填仓库地址 → Script Path 默认 `Jenkinsfile`。
3. 触发方式：代码提交自动触发 + **工作日每天 02:00 定时回归** + 手动传参（`BASE_URL` / `MARKER` / `WORKERS` / `RERUN` / `GENERATE_ALLURE`）。
4. 构建后可在任务页看到 `接口自动化测试报告(pytest-html)`，Allure 趋势图由 Allure 插件提供；
   `reports/**`、`logs/**` 已配置归档，失败可直接下载现场。

本地模拟 CI 全流程：

```powershell
.\.venv\Scripts\python.exe run.py -m regression -n 4 --rerun 1 --allure-report
```

## 10. 扩展：新增一个接口 / 一批用例（4 步）

以「新增收货地址-设为默认」为例：

```powershell
# 第 1 步：接口层加方法
#   api_objects/address_api.py
#   def set_default(self, address_id):
#       return self.post(f"{API_PREFIX}useraddress/default", data={"id": address_id}, idempotent=False)

# 第 2 步：数据层加用例（data/address_data.json）
#   {"desc": "正向-设为默认地址", "group": "default", "address_id": 1,
#    "expected_code": 0, "expected_msg": "设置成功"}

# 第 3 步：用例层加断言（tests/test_address.py）
#   @pytest.mark.regression
#   @pytest.mark.parametrize("case", build_params(load_cases("address_data.json", group="default")), ids=case_ids(...))
#   def test_address_default(address_api, temp_address, case):
#       res = address_api.set_default(temp_address["id"])
#       Assert.code(res, case["expected_code"], case["desc"])

# 第 4 步：运行验证
.\.venv\Scripts\python.exe -m pytest tests\test_address.py -k default -v
```

约定：接口可用性不确定时，给用例加 `@pytest.mark.requires("<能力名>")`，
并在 `core/env_check.py` 的 `Feature` 中登记，环境不具备即自动跳过。

约定：数据文件里**不要硬编码账号密码**，用 `${USER}` / `${PWD}` 占位符
（由 `core/data_loader.py` 自动替换为 config / 环境变量中的值），这样沙箱改密码只需要改一处配置。
同理可用 `${GOODS_ID}` 引用默认测试商品。
